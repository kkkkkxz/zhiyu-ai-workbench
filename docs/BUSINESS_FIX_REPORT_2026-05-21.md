# 业务问题修复报告

生成时间：2026-05-21 16:05:05  
项目：zwskchat 企业级 AI / ERP 协同平台

## 一、报告摘要

本次检查围绕“业务是否能正常闭环、接口是否存在明显越权或串数据风险”展开，重点覆盖工单、流程审批、AI 动作定义、数据权限、日程提醒、CRM 与合同等核心业务模块。

本轮已完成一批高优先级问题修复，主要解决以下风险：

- 用户可能查看或写入不属于自己的业务数据。
- 审批任务可能被非处理人操作。
- 流程发起后可能没有生成待办任务，导致业务卡死。
- 租户级配置可能被跨租户修改。
- 日程和提醒可能被请求参数错误改挂到其他用户。
- 客户、合同接口入参过宽，存在内部字段被前端覆盖的风险。

修复后，后端测试与前端类型检查均已通过。

## 二、已修复问题

### 1. 工单评论越权风险

涉及模块：工单管理

问题表现：

工单评论表不走自动租户隔离，原逻辑仅按工单 ID 查询或写入评论。如果攻击者或误操作方知道其他租户的工单 ID，存在读取或追加评论的风险。

修复措施：

- 查询评论前，先校验工单是否属于当前租户。
- 新增评论前，先校验工单是否可访问。
- 创建和更新工单时，固定当前租户、工单号、报告人等关键字段，避免被请求体覆盖。

业务收益：

降低工单数据串租户、评论误写入、客户服务记录泄露的风险。

### 2. 审批任务非本人可操作风险

涉及模块：流程审批

问题表现：

审批接口原先只根据任务 ID 查询待办，没有校验当前用户是否为任务处理人。如果用户猜到或拿到任务 ID，可能审批或驳回他人的任务。

修复措施：

- 审批和驳回前校验任务租户。
- 校验当前用户必须等于任务处理人。
- 非待处理任务不可重复处理。

业务收益：

保障审批责任边界，避免审批流被绕过，提升流程合规性。

### 3. 流程发起后可能无待办

涉及模块：流程审批

问题表现：

流程实例创建成功后，如果创建首个待办任务失败，原逻辑会吞掉异常，导致前端看到“发起成功”，但后续没有任何人能处理。

修复措施：

- 流程节点解析失败时明确抛错。
- 首个任务创建失败不再静默吞掉，会触发事务回滚。
- 流程实例和首个待办任务保持一致成功或一致失败。

业务收益：

避免流程卡死，减少人工排查“流程已发起但没人收到待办”的异常单。

### 4. AI 动作定义跨租户修改风险

涉及模块：AI 动作中心

问题表现：

AI 动作定义表属于租户忽略表，原更新和启停逻辑没有显式校验租户归属，存在跨租户修改动作定义的风险。

修复措施：

- 更新动作定义前校验当前租户归属。
- 启用或禁用动作定义前校验当前租户归属。
- 保留原租户字段和删除状态，避免请求体覆盖内部字段。

业务收益：

防止不同企业之间的 AI 动作配置相互影响，保障租户配置隔离。

### 5. 数据权限配置入口过宽

涉及模块：数据权限

问题表现：

数据权限配置接口原先只要求登录，没有限制管理员角色。普通用户理论上可能访问数据权限配置接口。

修复措施：

- 数据权限接口增加角色限制。
- 仅 `SUPER_ADMIN` 和 `TENANT_ADMIN` 可访问。

业务收益：

避免普通用户修改角色数据范围，保护组织权限体系稳定。

### 6. 日程和提醒归属可被覆盖

涉及模块：日程管理

问题表现：

日程更新和提醒创建直接接收实体，存在通过请求体传入 `userId`、`tenantId` 等字段，把记录改挂到其他用户或租户的风险。

修复措施：

- 创建日程和提醒时固定当前租户和当前用户。
- 更新日程时保留原租户和用户归属。
- 忽略提醒前校验提醒属于当前用户。

业务收益：

减少日程错挂、提醒误操作、个人工作安排泄露的风险。

### 7. CRM 与合同接口入参过宽

涉及模块：CRM、合同管理

问题表现：

客户、联系人、跟进记录、合同和合同里程碑接口原先直接接收数据库实体，前端可传入内部字段，容易造成租户、创建人、删除状态等关键字段被覆盖。

修复措施：

- 新增请求 DTO，改为白名单入参。
- 服务层补充租户归属、父对象存在性校验和默认值。
- 合同关联客户时校验客户必须属于当前租户。

业务收益：

提升接口可扩展性，降低未来字段增加后被误写入的风险，也让前后端契约更清晰。

## 四、当前仍需关注的问题

以下问题不影响本轮修复通过，但建议后续继续排期：

### 1. 生产配置存在真实密钥

当前配置文件中仍存在 API Key、JWT Secret、数据库密码等敏感信息。建议尽快迁移到环境变量或独立 secret 文件，并轮换已暴露密钥。

### 2. 仍有部分接口直接接收实体或 Map

工单、日程、工作流、AI 动作等模块仍有部分接口直接接收实体或 `Map`。本轮已在服务层补关键校验，但从长期扩展性看，建议逐步改为请求 DTO。

### 3. 部分中文注释和文案存在乱码

多个 Java 文件、配置文件和 SQL 注释中存在乱码。虽然目前不影响编译，但会降低维护效率，建议单独做一次编码清洗。

### 4. 权限模型还可以进一步细化

目前多个业务接口主要按“是否登录”控制。后续建议按业务动作细分权限码，例如：

- 工单创建、工单分派、工单关闭
- 合同创建、合同更新、合同删除
- 客户查看、客户编辑、客户删除
- AI 动作配置管理

## 五、业务结论

本轮修复重点解决了核心业务链路中的权限边界和数据归属问题。修复后，系统在多租户隔离、审批责任归属、流程一致性、日程个人数据保护、AI 动作配置隔离等方面更稳健。

整体判断：

- 当前代码可继续作为演示和内部试运行基础。
- 若准备上线或给真实客户试用，建议优先处理生产密钥、接口 DTO 化、权限码细化和乱码清理。
- 本轮修复覆盖的是“明显 bug”和“高概率业务不通点”，不是完整安全审计。
